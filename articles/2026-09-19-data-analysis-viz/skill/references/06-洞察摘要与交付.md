# 06 洞察摘要与交付

分析的价值不在"跑了多少图表"，而在"有人因为这份分析改变了动作"。所以交付物必须收敛到决策，而不是停在描述。

## 目录

1. 洞察摘要结构
2. 从统计量到洞察句
3. 图表清单与图注
4. 交付物清单
5. 交付自检

## 1. 洞察摘要结构

按决策报告组织，七段，顺序不要打乱：

```markdown
### 1. 结论与建议
一句话说明"该做什么"。如果只能记住一件事，就是这一句。

### 2. 量级与影响人群
多大、影响谁、占比多少。同时给绝对量和比例。

### 3. 证据与不确定性
哪几张图支撑这个结论；证据强度如何；样本量多少；有没有反例。

### 4. 因果状态
明确标注：这是**事实描述**、**相关关系**、**预测**，还是**因果结论**。
因果结论必须说明识别方式（随机实验 / 准实验设计 / 仅观测）。

### 5. 机制与假设
为什么会这样。如果只是假设，明确写"待验证"。

### 6. 行动、负责人与预期效果
谁做什么，预期影响多大，多久能看到。

### 7. 验证方式与护栏
怎么确认行动有效；哪些指标不能被牺牲（护栏）。
```

### 禁止的收尾方式

| 反模式 | 问题 |
|---|---|
| "以上就是本次数据分析的全部内容" | 只有描述没有决策 |
| "建议持续关注" | 没说关注什么、触发什么动作 |
| 罗列 20 个发现 | 没有优先级，读者无法行动 |
| 用相关当因果 | 会误导决策 |
| 只给结论不给量级 | 无法判断值不值得做 |

## 2. 从统计量到洞察句

统计量本身不是洞察。转换公式：

```text
洞察 = 事实（谁、多少、何时） + 意义（对目标意味着什么） + 行动（怎么办）
```

**示例对比：**

| 统计量输出 | 转化后的洞察 |
|---|---|
| 留存率 D7 = 18% | D7 留存 18%，低于上期 3 个点；下降主要来自 6 月新增渠道（该渠道 D7 仅 9%，占总新增 42%） |
| 相关系数 r = 0.72 | 使用时长的用户 7 日留存明显更高（r = 0.72，n = 12,400）；但两者都由"是否找到核心功能"驱动，需要先验证这一点再谈干预 |
| 偏度 = 2.4 | 时长分布严重右偏：T50 = 6 分钟但 T95 = 88 分钟；用均值 14 分钟描述会误导，应同时报中位数与 P95 |
| 前 10% 用户贡献 61% 收入 | 收入高度集中，前 10% 用户贡献 61%；需同时监控 TOP 付费用户的流失预警，并确认这不是单一大客户风险 |

**规则：**

- 每个洞察都要有"所以呢"。
- 不给量级的洞察是空话；不给行动的洞察是新闻稿。
- 一个摘要最多 5 条洞察，按重要性排序。
- 涉及因果的表述要降级到证据允许的强度（"相关""伴随""推测"），除非真有实验。

## 3. 图表清单与图注

**每张图配一句图注，格式固定：**

```text
[图 N] 结论式标题
这张图回答了什么问题 + 关键读数（带单位）
数据来源 / 样本量 / 口径 / 时间范围（如有必要）
```

**图注的写作要点：**

- 标题写结论，不写字段组合。✅"华东留存最高，西北最低" ❌"各地区留存率对比"
- 关键读数要写具体数字，不能只写"差异明显"。
- 单位、样本量、口径缺一不可。
- 数据处理有特殊之处（剔除异常值、对数轴、单位换算）要在图注里点明。

**图表清单表：**

| 编号 | 文件名 | 回答的问题 | 图型 | 结论 | 支撑数据 |
|---|---|---|---|---|---|
| 图1 | 01_趋势.png | 业务量是否在增长 | 折线图 | 7 月起增速由 12% 降至 3% | 01_趋势.csv |

## 4. 交付物清单

标准交付包：

```text
<项目目录>/
├── README.md              说明数据来源、口径、如何复现
├── 洞察摘要.md            决策报告（上面的七段结构）
├── data/
│   ├── raw/               原始数据（只读，不修改）
│   └── clean/             清洗后数据
├── scripts/
│   ├── profile_data.py    数据体检
│   ├── clean.py           清洗（含规则留痕）
│   ├── analyze.py         统计特征与指标
│   └── charts.py          绘图
├── outputs/
│   ├── figures/           PNG + SVG
│   ├── tables/            CSV（图表的支撑数据）
│   └── 数据体检报告.md
└── 验收/
    ├── 口径对照.md        每个指标的定义与分母
    └── 自检清单.md        逐项勾选
```

**每个交付物对应的责任：**

| 交付物 | 保证什么 |
|---|---|
| 洞察摘要 | 有人知道该做什么 |
| 图表 + 支撑 CSV | 结论可核 |
| 绘图脚本 | 结果可复现 |
| 口径对照 | 换个分析师能算出一样的数 |
| 数据体检报告 | 别人知道数据有什么坑 |
| 自检清单 | 质量标准被真正执行过 |

**版本与物料管理：**

- 只保留一套最新完整物料；版本、更新时间、状态写在文档或元数据里，不靠文件名堆版本号。
- 新版验证通过后替换旧版，清理过时草稿与中间产物。
- 最新正文仍引用的图片、原始数据、依赖与映射属于当前物料，不因文件名版本较低而删除。
- 历史版本用 Git 追溯，不在目录里另存 N 份副本。

## 5. 交付自检

**内容**

- 每张图都回答一个明确问题吗？标题写的是结论吗？
- 每个结论都标了量级吗？
- 因果状态标注清楚了吗（事实/相关/预测/因果）？
- 有没有把仅作诊断的前后对比当成因果证据？
- 比率都交代分母了吗？用的是加权聚合吗？
- 偏态数据用中位数和分位数了吗？
- 引言、图注、正文与实际图表内容一一对应吗（不能出现"堆叠柱状图"实际是分组柱状图的错配）？

**质量**

- 代码实际运行过吗？报错都解决了吗？
- 图表同时检查了脚本无报错**和**图形结构是否符合定义？
- 图片按小节逐一核对过实际内容吗（不能只靠文件名和上传顺序推断）？
- 有不确定性的地方标注了吗？
- 已知局限与未完成的部分如实说明了吗？

**合规**

- 没有写入真实密钥、Token、Cookie、密码或内部地址吗？
- 示例统一用明显占位符（如 `https://gateway.example.com`、`sk-your-key`）吗？
- 涉及个人隐私的数据只做聚合了吗？
- 涉及地图时使用了符合国家标准的正确地图数据吗？
- 涉及软件版本、价格、政策时核对过现行官方资料吗？

**交付沟通**

- 明确区分了"已完成并核对""待人工处理""待确认"吗？
- 没有实际核验的状态没有写成"已通过"吗？
- 交付的语言和篇幅与受众匹配吗（给管理层的一页结论 ≠ 给分析师的完整方法）？
