# 搭建带数据与管理后台的网站

把用户需求变成可运行项目，帮助不懂技术的人完成账号配置和验收。优先免费起步，明确费用和额度边界。使用用户选定技术；既有项目先读项目说明，不强制改造成新模板。

## 需求与范围

- 先判断新建还是修改已有站点，读仓库说明、工作区状态与现有部署配置。
- 明确内容字段、公开页面、后台动作、管理员来源、预期数据与图片规模、个人非商业或商业用途。能合理推断的先推进；只问会影响实现的缺失信息。
- 无指定时，以个人资料库为示例：列表、搜索、分类、详情，管理员新增、修改、隐藏、图片上传；先完成最小闭环。不要擅自加入支付、会员、爬虫、AI 接口或公开注册。
- 用小白能理解的语言维护短计划，每个需要用户操作的步骤都给入口、填写项、预期结果。

## 架构选择

- GitHub 保存代码与版本；Vercel 托管页面和接口；Supabase 保存 PostgreSQL 数据和 Storage 文件。登录优先 Supabase Auth。按复杂度选择简单静态前端加函数或支持 Vercel 的成熟框架，不为演示堆叠框架。
- Cloudflare 默认作为可选的自定义域名 DNS 管理方。无域名时先使用 Vercel 默认地址，不强制购买域名。
- 新项目默认优先用用户会话与 RLS 约束数据访问。确需服务端 secret key 时，单独创建仅服务端使用的客户端，并在每个接口验证身份、管理员授权、输入和允许操作的对象；公开接口限定字段、发布状态和页大小。服务端高级密钥会绕过 RLS，不可把 RLS 当成这些接口的授权替代。
- 将现有项目的真实实现与建议方案分开描述。不要复制其他项目的域名、项目 ID、账户、密码、业务数据或历史破坏性迁移。

## 开始前核对

读取 [平台接入与维护](references/platforms.md) 中当前阶段相关部分，联网检查官方免费用途、配额、密钥类型与部署文档，记录日期。检查 Supabase 相关变更日志。网络不可用时标明待核验，避免保证永久免费或任意商业使用免费。

## 实现顺序

1. 创建真实项目文件、依赖锁文件、README、只含占位符的 `.env.example`、数据库初始化/迁移及权限脚本。样例数据标为演示，不假装来自生产。
2. 本地先完成页面流程；演示模式必须显式标识。生产缺少数据库配置时返回可理解的配置错误，不能静默回退演示数据冒充成功。
3. 建表包含唯一主键、必要约束、发布状态和时间字段。依据实际查询建立索引，列表使用有限页大小与唯一字段参与的稳定排序。批量导入明确冲突处理，不能反复导入造成重复。
4. 提供第一个管理员的实际创建办法：在 Supabase Auth 建账号，在服务端配置或不可由普通用户修改的表中授予管理权限。不要将“已登录”等同“管理员”，不要依赖用户可编辑的 `user_metadata` 或浏览器 localStorage 标记授权。仅需后台时关闭公众注册。
5. 对暴露 schema 的表启用 RLS，最小化角色授权，按真实访问模型写策略；UPDATE 同时考虑 SELECT、USING 与 WITH CHECK。策略中的管理员判定必须来自受保护来源，避免自引用递归。不要为修复权限报错直接放开所有读写。
6. 图片桶的读取权限与内容一致。公开封面可公开读；写入、覆盖和删除均检查管理员。限制文件类型和大小，使用随机路径并处理失败，不以客户端传来的 MIME 类型作为唯一判断。私人文件使用私有桶与短时签名访问。
7. 接通真实数据库后验证读取、管理员增改隐藏、图片上传和刷新保留。登录及管理响应禁止共享缓存；公开内容按允许延迟设置缓存并说明更新机制。所有用户内容按文本安全渲染，上传错误不回显密钥。
8. 本地构建、检查和测试通过后，在既有授权内提交/推送/部署；需要用户登录的平台列出明确动作，独立的本地工作继续做完。

## 凭据与外部动作

- 新 Supabase 项目按当前官方文档选择 publishable/secret key；兼容旧项目时辨认 anon/service_role，不能随意互换。secret/service_role、数据库密码不能进入浏览器构建、公开仓库、截图或报告。
- 环境变量名与实际代码一致。前端公开前缀会将变量交给浏览器，绝不能用于服务端高级密钥。
- 让用户在平台密钥设置、凭据管理器或受保护本地配置中填写机密；不要求在聊天中粘贴密码。日志仅报告配置是否存在，不输出值。
- 用户要求“搭建”不自动授予购买域名、付费升级、公开私有仓库或改动其他项目的权限。已授权的创建、推送、部署无需重复确认；GitHub 推送可能触发已连接的生产部署，提前辨认分支与目标。
- 域名接管先检查已有 DNS 记录，保留邮件和无关服务。初次连接 Vercel 默认 DNS only；记录值从当前目标项目获取。代理/缓存/Worker 只有有实际需求才增加，禁止缓存认证响应或使用宽泛规则将后台/API 全部缓存。
- 生产数据库先识别现有表和数据，再规划可审阅迁移；需要删除、覆盖数据时遵守用户的实际授权，不把空库教程执行到已有数据库。

## 验收与交付

按 [验收与故障定位](references/acceptance.md) 进行与本次改动相称的验证。一次完整新站至少检查：游客公开读取，草稿不可见，普通账号和匿名请求不能写，管理员可维护，图片权限，分页不重漏，重新加载后数据保留，桌面/手机布局及控制台错误。

实际测试对应的场景；只有 mock 测试时不能声称真实 RLS、云端登录或生产部署已验证。云端缺少授权时交付本地项目、可执行配置步骤和清楚的剩余项，不伪造测试账号或成功回执。

README 写明安装/启动/构建命令、数据库初始化顺序、第一位管理员创建、环境变量表、Vercel 导入设置、可选域名接入、数据与文件备份和恢复办法。备份说明区分代码、数据库与 Storage 文件。

最终逐项报告本地文件、测试证据、本地提交、远程推送、部署目标/版本与公网功能验证；未完成阶段明确保留。交付用户能实际打开的结果及下一步必要操作，不能仅列计划结束。
